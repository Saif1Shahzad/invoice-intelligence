# Live Vercel deployment

The application now has a Vercel container deployment using the existing `frontend` project directory. It builds the React frontend and Python FastAPI backend together, includes native Tesseract and stores durable records in Neon PostgreSQL and artifacts in private Vercel Blob. `/tmp` is only a hash-verified download/render cache.

Use `frontend/Dockerfile.vercel` and `frontend/vercel.json` with the Container framework and Root Directory `frontend`. A reproducible Python wheel in `frontend/vendor` packages the authoritative backend source from `src/`. The root Dockerfile is also supplied for independent full-repository builds. Vercel's container runtime is currently beta and supported on all plans.

Required private runtime configuration:
- `DATABASE_URL`: PostgreSQL connection string (sensitive).
- `BLOB_READ_WRITE_TOKEN`: private Blob store credential, generated by the Vercel storage connection.
- `GROQ_API_KEY`: extraction provider credential (sensitive).
- `INVOICE_ACCOUNTS_JSON`: salted scrypt account hashes (sensitive). Never ship plaintext passwords.
- `INVOICE_PUBLIC_ORIGIN` and `INVOICE_ALLOWED_HOSTS`: restrict to the actual frontend origin/hostname.
- `INVOICE_CLOUD=vercel`, `EXTRACTION_PROVIDER=groq`.

The frontend defaults to live mode in the container build. The entire application requires sign-in. An explicitly labeled sample mode remains available after sign-in.

## Processing model and pilot limits

Processing runs during bounded HTTP invocations of `POST /v1/documents/{id}/process`. The open workspace requests these stages and polls state. Nothing is left running after the HTTP response. Saved jobs are durable; if a request or browser stops, lease expiry and a later workspace visit allow recovery. This version does **not** promise unattended background processing after the browser closes. A native durable queue/daemon is a future improvement.

Each upload is limited to 3.5 MB and 3 pages for this initial Vercel pilot. File-type, pixel, parser timeout, evidence and arithmetic checks still apply. The backend preserves the original local deployment and SQLite workflow unless `INVOICE_CLOUD=vercel` is explicitly set.

Groq daily limits remain external to Vercel. Rate-limit responses persist a retry time and never produce a confirmed invoice. Use the advanced review interface at `/legacy-review` for PO imports, duplicate pair decisions, timers, reopen and rebase.

## Persistence and concurrency

The cloud adapter uses PostgreSQL transactions and an advisory lock for domain writes, matching the single-writer model of the original pilot. Inference runs outside database transactions. Append-only audit tables are enforced by database triggers. Original files and per-attempt outputs are immutable in Blob; downloaded bytes are verified against their stored SHA-256. Cloud changes require integration tests against actual PostgreSQL/Blob, not only SQLite tests.

Existing local invoices are not silently uploaded. The cloud database starts separately. Backups and user-management changes must use the cloud database/provider tools; the original offline SQLite backup command applies to local mode only.
